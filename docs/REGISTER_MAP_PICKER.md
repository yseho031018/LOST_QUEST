# 등록 장소 지도 선택

## 동작과 범위

PC·모바일 등록 1단계의 상세 장소 아래 `지도에서 찾기`를 선택하면 지도가 열립니다. 지도를 여는 것만으로 장소 검색은 실행하지 않습니다. 검색어를 입력한 후 검색 버튼 또는 Enter로 검색하고, 결과나 지도 핀을 선택한 뒤 `이 장소 사용`으로 확정합니다. 지도 중심 선택 버튼으로 키보드에서도 핀을 선택할 수 있습니다. Escape·취소는 초안을 버립니다.

선택은 필수가 아닙니다. 빈 상세 장소는 기존 필수 검증으로 차단하며, 검색·지도 연결이 실패해도 직접 입력하여 등록할 수 있습니다. 검색 결과의 공식 시·도 명칭만 기존 지역 목록으로 정규화합니다. 핀 이동은 역지오코딩을 하지 않으므로 장소 문구를 사용자가 확인해야 합니다. 지역이나 상세 장소를 편집하면 확정된 좌표를 해제합니다.

`latitude`, `longitude`는 둘 다 생략하거나 유효한 유한 수 쌍(위도 -90~90, 경도 -180~180)이어야 합니다. JSON·사진 multipart의 item 파트 모두 동일합니다. 새 분실·습득물 생성 시에만 좌표를 받습니다. 기존 수정 API는 제목 등만 바뀌면 좌표를 보존하고 지역·장소가 바뀌면 해제합니다. 기존 텍스트 게시물은 NULL 그대로 유지하며 일괄 위치 추정은 하지 않습니다.

상세 페이지는 사용자 저장 좌표를 우선 표시합니다. 좌표가 없는 게시물의 검토된 근사 위치와 카카오맵 링크는 기존 동작을 유지합니다. 인증·숨김·반환·검색·AI 매칭 정책은 변경하지 않습니다.

## 장소 검색과 운영 조건

사용자가 무료 OSM/Nominatim의 사용 조건에 동의한 후 연결했습니다. 로그인한 등록 사용자만 `GET /api/places/search?q=...`를 사용할 수 있습니다. 브라우저는 Nominatim에 직접 검색하지 않습니다. 서버가 한국 범위, 한국어, 최대 5개로 검색하고 필수 필드만 응답합니다. 검색어는 2~100자이며 검색어·토큰을 별도로 로그에 남기지 않습니다. 개인정보 입력 금지와 OSM 출처를 UI에 표시합니다.

단일 백엔드 인스턴스 전체에서 동시 외부 요청 1개, 시작 간격 최소 1.1초, 24시간당 최대 1,000회로 제한합니다. 성공·빈 결과를 정규화된 검색어별 24시간 캐시(최대 256개)하며 실패 응답은 캐시하지 않습니다. 응답 본문은 256KB, HTTP 전체 완료는 6초로 제한합니다. 제한 시 429, 외부 오류·비활성화 시 503을 안내하며 자동 재시도·자동완성·일괄 검색은 없습니다.

캐시·호출 제한은 메모리 기반으로 재시작 시 초기화됩니다. **복수 JVM/인스턴스 운영은 지원하지 않습니다.** 여러 인스턴스로 확장하려면 앱 전체의 공유 제한·캐시 또는 다른 공급자가 필요합니다. 공개 서비스는 가용성 보장이 없으며 행사 전 실제 장소 검색 품질을 확인해야 합니다. 장시간·상시 운영과 트래픽 증가 시 별도 공급자 또는 자체 호스팅을 검토합니다.

서버 환경변수 `PLACE_SEARCH_ENABLED=false`로 검색을 끄고 텍스트 등록은 유지할 수 있습니다. `PLACE_SEARCH_URL`은 기본 `https://nominatim.openstreetmap.org/search`이며 운영자가 검토한 호환 HTTPS 공급자로 교체할 수 있습니다. 사용자 입력으로 URL을 받지 않으며 리다이렉트를 따르지 않습니다. User-Agent에 앱 이름과 저장소 연락 경로를 포함합니다. 지도 타일은 기존 Leaflet/OSM의 일반 브라우저 캐시를 사용하며 선다운로드·오프라인 수집은 하지 않습니다.

## 운영 반영 순서 — 아직 실행하지 않음

1. 실제 DB 식별, 스키마·행 수 확인, 복구 가능한 백업 검증, 사용자 승인 확보.
2. `backend/sql/registration-coordinates.sql` 사전 조회 검토. 각 테이블에 두 컬럼이 모두 없을 때만 해당 ALTER 실행. 부분 적용·이미 존재·타입 차이가 있으면 중단. MySQL DDL은 자동 커밋이며 트랜잭션 롤백할 수 없음.
3. 두 테이블의 nullable DOUBLE 컬럼 4개와 기존 데이터 보존 확인. 새 백엔드를 `ddl-auto=validate`로 검증한 후 승인된 서버 교체. 기존 JAR·환경·CORS·업로드 경로 보관.
4. 새 API·인증·텍스트 등록 호환성을 전용 테스트 데이터/별도 승인으로 확인한 뒤 PC·모바일 프론트엔드 배포. 구형 JAR은 알 수 없는 좌표 필드를 무시하므로 프론트만 먼저 배포하면 좌표가 저장되지 않을 수 있음.
5. 실패 시 원인을 검토하고 기존 JAR과 프론트를 복구. 추가한 nullable 컬럼은 남겨두며 실제 DB 복원·컬럼 삭제를 임의로 수행하지 않음.

이 작업에서는 실제 DB ALTER·실제 게시물 생성·운영 백엔드 재시작·터널 변경·커밋·푸시·Sites 배포를 수행하지 않습니다. 별도 기능 worktree에서 기존 미커밋 파일을 보존합니다.

## 재현 가능한 로컬 검증

각 프론트엔드 폴더에서 `npm test`, `npx tsc -b`, `npm run build`. 빌드에는 기존 배포의 API 주소/원격 AI 모델 환경변수를 유지해야 합니다. 검증 산출물을 운영 dist로 복사하지 않습니다.

backend에서 `mvn test` 실행. `application-test.yml`의 H2 메모리 DB와 비활성화된 Nominatim 설정을 사용합니다. 환경에 `LOSTQUEST_RETURN_CONCURRENCY_DB_URL`이 있으면 반드시 H2 메모리 URL로 명시적으로 덮어씁니다. `mysql-it` 프로필을 사용하지 않습니다. 새 검색 서비스 테스트는 127.0.0.1의 모의 HTTP 서버만 호출합니다.

브라우저 검증은 모의 인증·목록·검색·등록 API를 사용하여 PC 및 모바일 390px에서 실시합니다. 실제 DB에 쓰지 않습니다. 실제 모바일 터치 동작·현장 네트워크·Nominatim 검색 품질은 운영 반영 전 추가 확인이 필요합니다.
